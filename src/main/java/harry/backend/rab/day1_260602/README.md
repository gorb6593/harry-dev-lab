# Day 1: 재고를 포함한 주문 API

## 목표

오늘의 과제는 단순 CRUD가 아니다. 주문 생성과 취소 과정에서 재고 정합성을 지키는 REST API를 구현한다.

이 과제를 통해 다음 항목을 확인한다.

- Spring MVC 기반 API 설계
- 계층별 책임 분리
- 요청 검증과 일관된 예외 응답
- JPA 엔티티 설계와 트랜잭션 경계
- 비즈니스 규칙을 코드로 표현하는 방식
- 핵심 로직의 테스트 전략

구현 파일은 모두 `harry.backend.rab.day1_260602` 하위 패키지에 둔다. 하위 패키지 구조는 직접 설계한다.

## 도메인

온라인 상점에서 상품을 등록하고 주문할 수 있어야 한다.

### 상품

상품은 아래 정보를 가진다.

- `id`: 식별자
- `name`: 상품명
- `price`: 가격
- `stockQuantity`: 판매 가능한 재고 수량

### 주문

주문은 아래 정보를 가진다.

- `id`: 식별자
- `productId`: 주문한 상품 식별자
- `quantity`: 주문 수량
- `orderAmount`: 주문 시점의 총 금액
- `status`: `CREATED` 또는 `CANCELED`
- `createdAt`: 주문 생성 시각
- `canceledAt`: 취소 시각. 취소 전에는 `null`

## 요구사항

### 1. 상품 등록

`POST /api/day1/products`

요청 예시:

```json
{
  "name": "Mechanical Keyboard",
  "price": 120000,
  "stockQuantity": 10
}
```

규칙:

- 상품명은 공백을 제외하고 비어 있을 수 없다.
- 가격은 0보다 커야 한다.
- 초기 재고는 0 이상이어야 한다.
- 성공하면 HTTP `201 Created`를 반환한다.

### 2. 상품 단건 조회

`GET /api/day1/products/{productId}`

규칙:

- 존재하지 않는 상품이면 HTTP `404 Not Found`를 반환한다.

### 3. 주문 생성

`POST /api/day1/orders`

요청 예시:

```json
{
  "productId": 1,
  "quantity": 3
}
```

규칙:

- 주문 수량은 1 이상이어야 한다.
- 존재하지 않는 상품은 주문할 수 없다.
- 재고보다 많은 수량은 주문할 수 없다.
- 주문 생성과 재고 차감은 하나의 트랜잭션에서 처리한다.
- `orderAmount`는 주문 시점의 `상품 가격 * 주문 수량`으로 저장한다.
- 성공하면 HTTP `201 Created`를 반환한다.

### 4. 주문 단건 조회

`GET /api/day1/orders/{orderId}`

규칙:

- 존재하지 않는 주문이면 HTTP `404 Not Found`를 반환한다.

### 5. 주문 취소

`POST /api/day1/orders/{orderId}/cancel`

규칙:

- 주문 상태를 `CANCELED`로 변경한다.
- 주문 생성 때 차감했던 재고를 복구한다.
- 이미 취소된 주문은 다시 취소할 수 없다.
- 주문 상태 변경과 재고 복구는 하나의 트랜잭션에서 처리한다.
- 성공하면 HTTP `200 OK`를 반환한다.

## 공통 에러 응답

모든 실패 응답은 아래 JSON 형식을 사용한다. 필드명은 `camelCase`로 작성한다.

```json
{
  "code": "INSUFFICIENT_STOCK",
  "message": "재고가 부족합니다.",
  "path": "/api/day1/orders",
  "timestamp": "2026-06-02T10:30:00"
}
```

최소한 아래 에러를 구분한다.

| 상황 | HTTP 상태 | `code` |
| --- | --- | --- |
| 요청 값 검증 실패 | `400 Bad Request` | `INVALID_REQUEST` |
| 재고 부족 | `409 Conflict` | `INSUFFICIENT_STOCK` |
| 이미 취소된 주문 | `409 Conflict` | `ORDER_ALREADY_CANCELED` |
| 상품 없음 | `404 Not Found` | `PRODUCT_NOT_FOUND` |
| 주문 없음 | `404 Not Found` | `ORDER_NOT_FOUND` |

## 제약 조건

- Java 17과 Spring Boot 3.x 기준으로 구현한다.
- API JSON 필드명은 `camelCase`를 사용한다.
- Controller는 HTTP 요청과 응답 변환에 집중한다.
- 트랜잭션 경계는 애플리케이션 서비스에 둔다.
- 엔티티의 상태를 외부에서 무분별하게 변경하지 않는다.
- 비즈니스 규칙은 가능한 한 해당 상태를 소유한 객체에 둔다.
- Controller에서 Repository를 직접 호출하지 않는다.
- 엔티티를 API 응답으로 직접 반환하지 않는다.
- DB 동시성 문제 해결은 오늘의 필수 범위가 아니다. 단, 현재 구현의 한계를 설명할 수 있어야 한다.

## 완료 조건

- [ ] 상품 등록 후 상품을 조회할 수 있다.
- [ ] 주문 생성 후 상품 재고가 감소한다.
- [ ] 주문 금액이 주문 생성 시점 기준으로 저장된다.
- [ ] 재고를 초과한 주문은 실패하고 재고가 변경되지 않는다.
- [ ] 주문 취소 후 상품 재고가 복구된다.
- [ ] 동일 주문의 두 번째 취소는 실패하고 재고가 추가로 증가하지 않는다.
- [ ] 존재하지 않는 상품과 주문에 대해 `404` 응답이 반환된다.
- [ ] 요청 값 오류에 대해 `400` 응답이 반환된다.
- [ ] 공통 에러 응답 형식이 모든 실패 응답에서 유지된다.
- [ ] 핵심 비즈니스 규칙을 자동화 테스트로 검증한다.

## 직접 실행

1. MySQL을 실행한다.

```bash
docker compose up -d
```

2. 애플리케이션을 실행한다.

```bash
./gradlew bootRun
```

3. 같은 디렉터리의 `day1.http`를 IntelliJ HTTP Client에서 순서대로 실행한다.

4. 자동화 테스트를 실행한다.

```bash
./gradlew test
```

## 생각해 볼 질문

구현을 마친 뒤 아래 질문에 답할 수 있어야 한다.

1. 주문 취소 로직을 Controller가 아니라 Service에 둔 이유는 무엇인가?
2. 재고 차감 로직을 엔티티 메서드로 구현했는가? 그렇게 판단한 이유는 무엇인가?
3. `@Transactional`이 필요한 메서드는 무엇이며, 읽기 전용 트랜잭션은 어디에 적용했는가?
4. 주문 생성 도중 예외가 발생하면 재고 차감은 어떻게 롤백되는가?
5. 동시에 두 요청이 마지막 재고를 주문하면 현재 구현에서 어떤 문제가 생길 수 있는가?
6. API 응답 DTO와 엔티티를 분리한 이유는 무엇인가?
7. 단위 테스트와 통합 테스트의 경계를 어떻게 나누었는가?
