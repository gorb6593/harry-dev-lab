# Day 1: 재고 차감 동시성 문제 진단과 해결

## 오늘의 평가 방식

빈 프로젝트에서 CRUD를 모두 만드는 과제가 아니다. 제공된 코드를 읽고, 테스트로 문제를 재현하고, 핵심 부분을 직접 수정한다.

오늘 확인할 역량은 다음과 같다.

- 기존 코드의 호출 흐름을 빠르게 파악하는 능력
- JPA 변경 감지와 트랜잭션 경계를 설명하는 능력
- 동시성 문제를 테스트로 재현하는 능력
- 해결 방식의 장단점을 비교하고 하나를 선택하는 능력
- 선택한 방식이 실제로 동작하는지 검증하는 능력

## 실행 순서

먼저 아래 테스트를 실행한다.

```bash
./gradlew test --tests '*StockServiceConcurrencyTest'
```

초기 상태에서는 테스트가 실패해야 한다. 재고 20개에 대해 20개 요청이 동시에 1개씩 차감하지만 최종 재고가 0이 되지 않는다.

`decreaseWithProcessingDelay()`의 지연 시간은 운영 기능이 아니다. 경쟁 상태를 재현하기 위한 실습 장치다.

## 필수 과제

### 과제 1. 원인 분석

코드를 수정하기 전에 아래 내용을 설명한다.

1. `StockService.decreaseWithProcessingDelay()`에서 어떤 순서로 조회와 변경이 일어나는가?
2. `stockItemRepository.save()`를 다시 호출하지 않아도 수량 변경이 DB에 반영되는 이유는 무엇인가?
3. 메서드에 `@Transactional`이 있어도 동시성 문제가 해결되지 않는 이유는 무엇인가?
4. 여러 트랜잭션이 동일한 초기 재고 값을 읽으면 어떤 갱신 유실이 발생하는가?

### 과제 2. 해결책 선택

아래 방식 중 하나를 선택하여 구현한다.

- 비관적 락
- 낙관적 락과 재시도
- 단일 SQL 조건부 업데이트

선택한 방식이 오늘의 요구사항에 적절한 이유와, 선택하지 않은 방식의 장단점을 설명한다.

### 과제 3. 구현과 검증

필요한 파일만 수정하거나 추가한다. 아래 테스트가 통과해야 한다.

```bash
./gradlew test --tests '*StockServiceConcurrencyTest'
```

## 제약 조건

- Java 17과 Spring Boot 3.x를 기준으로 한다.
- Controller에서 Repository를 직접 호출하지 않는다.
- 테스트의 assertion을 약화하거나 삭제해서 통과시키지 않는다.
- 테스트의 동시 요청 수를 줄이거나 지연 시간을 제거해서 통과시키지 않는다.
- `synchronized`만 추가하는 방식은 사용하지 않는다. 애플리케이션 인스턴스가 여러 개인 환경을 설명할 수 없기 때문이다.
